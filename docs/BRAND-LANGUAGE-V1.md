# TBSP brand language — V1 direction

Updated: 7 September 2026  
Status: Aligned creative direction; not an approved identity or final logo  
Applies to: Website, product marketing, documentation, presentations, technical content, sales collateral, events, and launch campaigns

## 1. The recommendation

Make complex engineering work feel understandable, connected, and under control.

The creative direction is **engineering, made legible**. This is an internal design brief, not a proposed final tagline. Build the identity around warm paper, dark ink, precise typography, a restrained oxide accent, and a traceable path connecting real work artifacts. Give the product enough visual presence to demonstrate how it works.

The desired first impression is: “These people understand the complexity of our engineering organisation, and I can see how their product helps.” The desired second impression is: “I can inspect the workflow, the evidence, and the controls.”

This recommendation is design judgment based on the ICP and the reference sites, not evidence that a particular aesthetic improves conversions.

## 2. Who the design must work for

| Audience | What they need to feel or understand | Design response |
|---|---|---|
| CTO, VP Engineering, GCC head | The product is substantial, relevant to an existing engineering organisation, and understandable | Strong hierarchy, controlled composition, concise outcomes, real workflows, clear Capillary relationship |
| Platform/DevEx owner, architect | The system has coherent boundaries and fits the existing stack | Legible architecture, source and integration labels, visible handoffs, documentation within reach |
| Developer, tech lead, reviewer, SRE | There is a usable product behind the claims | Readable interface crops, realistic examples, visible inputs and outputs, source references, quick access to technical detail |
| Security and governance approver | Actions, data, permissions, and human decisions can be examined | Precise data-flow diagrams, clear state distinctions, approval records, structured security content |

The brand addresses people responsible for software that already exists and already matters. Calmness, specificity, and legibility should survive every channel. Developer-facing material can be denser; executive material can be more concise. Both use the same visual system.

## 4. Brand character and voice

Four attributes: **composed, precise, connected, human**.

- Composed: measured space, a stable layout, and deliberate emphasis.
- Precise: concrete inputs, actions, outputs, and boundaries.
- Connected: shared context and work continuity are visible throughout the system.
- Human: acknowledge the people responsible for decisions and outcomes.

Write as an experienced engineering colleague explaining a system to another capable person. Use active verbs: understand, define, build, review, investigate, approve, connect. Introduce the concrete job before terms such as outer loop or agentic delivery.

Use **agentic software development platform for enterprise engineering** as the working category in analyst and market-facing material. Use software-delivery and lifecycle language to explain the broader product. Keep “outer loop” as supporting vocabulary rather than the homepage category.

### Draft copy specimens

| Location | Example |
|---|---|
| Homepage headline | Ship with the whole picture. |
| Homepage explanation | Shared engineering context, executable workflows, and human approvals—from requirements to production. |
| Platform | Carry the context into every next step. |
| Spec | Turn the next request into development-ready work. |
| Code | Build and debug with your system in view. |
| Review | Review the change with the reason behind it. |
| On-call | Investigate the alert with the context behind it. |
| Surfaces | Use the same context wherever your team works. |
| TBSP in Slack | Ask in Slack. Follow the answer to its source. |
| Security | See what runs, what it can access, and who approves it. |

These are draft language specimens. Final product copy must match the demonstrated workflow. Prefer an exact description over vague claims such as “unlock limitless productivity.” Quantified results require evidence; product examples need to distinguish hypotheses, findings, and approved actions.

Use sentence case for headings and buttons. Reserve capitals and mono labels for short metadata. Keep paragraphs short and explain each diagram in ordinary language. Humour can appear in community content when it arises naturally; incident, permission, and failure messages should remain direct and useful.

## 5. Colour system

Recommended starting palette; these are original proposed values, not copied from the references.

| Token | Value | Role |
|---|---|---|
| Paper | `#F5F3EC` | Default marketing background and reading surface |
| White | `#FFFFFF` | Documents, selected detail surfaces, text on primary buttons |
| Ink | `#202622` | Main text, wordmark, strong structural elements |
| Muted ink | `#5D655E` | Secondary copy and metadata on paper/white |
| Rule | `#D6D9D0` | Decorative separators and nonessential grid lines |
| Control boundary | `#788078` | Input boundaries and meaningful neutral diagram edges on paper |
| Oxide | `#B8432F` | Primary action, active path, selected module marker, editorial emphasis |
| Oxide tint | `#F2DCD4` | Quiet selected-state background with dark text |
| Dark field | `#18211D` | Technical specimens, product-stage backgrounds, selected brand moments |
| Light oxide | `#EF9A83` | Accent text and paths on dark fields |
| Dark-field secondary text | `#B8C4BC` | Supporting labels on dark fields |
| Success | `#2E6A4F` | Confirmed/approved outcome on light surfaces, always with a label or symbol |
| Caution | `#8A5A10` | Pending attention or warning on light surfaces, with explicit label |
| Error | `#9F2941` | Failure on light surfaces, with explicit label |

Use approximately 75% light neutral field, 20% dark or ink structure, and 5% chromatic emphasis as a composition starting point. These are visual proportions, not quotas to enforce on every asset.

Oxide is the brand accent, not an error code. Error and approval states must have explicit text and distinct symbols. Do not assign unrelated brand colours to the four modules or individual surfaces. They belong to one platform.

The marketing site should be predominantly light. Dark technical panels introduce focus and support terminal/code imagery. Even if the name becomes The Black Screen Project, the entire site does not need a black background. Existing product screenshots retain their real interface theme.

A cooler cobalt (`#2D50C7`) is a viable alternative accent if the team strongly prefers a more conventional technology tone. Oxide is the recommendation because it adds warmth to the precise engineering structure. Choose one master accent after visual review.

### Contrast guardrails

Computed sample pairs: ink/paper 13.89:1; muted ink/paper 5.42:1; white/oxide 5.41:1; oxide/paper 4.87:1; light oxide/dark field 7.55:1. These checks validate those pairs only, not an entire interface.

Use at least 4.5:1 for ordinary text and 3:1 for qualifying large text, consistent with [W3C's contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). Faint rules are decorative; do not rely on them as the only boundary for an input or meaningful diagram relationship. Dark-mode status colours require their own accessible variants and verification.

## 6. Typography

Use **IBM Plex Sans** for headlines, body text, navigation, and controls, paired with **IBM Plex Mono** for code, artifact IDs, file names, timestamps, and small technical labels. IBM distributes Plex under the Open Font License and provides Sans and Mono families in its [official repository](https://github.com/IBM/plex).

This pairing is a proposed practical starting point. Its technical character should come from controlled use, not a page filled with monospace text. A custom or licensed headline face can be evaluated later if the identity needs more typographic distinctiveness; it is not necessary for V1 consistency.

| Role | Desktop starting point | Mobile starting point | Weight / rhythm |
|---|---|---|---|
| Hero headline | 60–72 px | 36–42 px | 500; 1.04–1.1 line height; modest negative tracking |
| Section heading | 36–44 px | 28–32 px | 500; 1.15 line height |
| Lead paragraph | 20–22 px | 18–20 px | 400; 1.45–1.55 line height |
| Body | 18 px | 16–18 px | 400; 1.55–1.65 line height |
| Navigation/control | 15–16 px | 16 px | 400/500; readable, sentence case |
| Technical label | 12–14 px | 12–14 px | Mono 400/500; short only |

Aim for 55–75 characters per line for explanatory prose. Keep headlines to a few deliberate lines; use responsive line wrapping rather than forcing desktop breaks on phones. Do not reproduce Hebbia's serif-led identity simply to signal “enterprise.”

## 7. Layout, shapes, and components

- Use a 12-column desktop grid with a content width around 1200–1280 px; collapse to a simple single column on small screens.
- Use an 8 px spacing rhythm with a 4 px half-step. Starting section spacing: 96–128 px desktop and 48–64 px mobile.
- Prefer strong alignment, readable text, flat surfaces, and thin rules. Every container must group actual information.
- Use 4–6 px corner radii for controls, 8 px for product frames, and square or minimally rounded document artifacts. Avoid mixing pills, soft bubbles, and sharp frames without a functional reason.
- Keep primary buttons solid oxide with white text; secondary buttons use a clear neutral boundary. Text links are visibly identifiable and have clear hover and focus states.
- Use shadows sparingly for true overlap or an opened menu. Do not give every section a floating-card treatment.
- Provide explicit selected, hover, pressed, loading, disabled, focus, error, and success states in the component library. Keep the action label understandable while loading.
- Navigation remains conventional and keyboard accessible. Long explanations do not depend on hover, animation, or a carousel.

The signature is the relationship between elements: aligned artifacts, small annotations, and a consistent highlighted path. An ordinary button or card does not need novelty.

## 8. Graphic language: a traceable path through real work

The recurring motif is one work item retaining its context as it moves through the organisation. Use the same artifact identifier across Spec, Code, Review, release, and On-call, with the investigation handing corrective work back to Code. Desktop, terminal, Slack, Teams, and mobile are access surfaces around this shared record rather than lifecycle stages.

Build the visual vocabulary from five primitives:

1. **Artifacts:** flat rectangular documents or interface excerpts with short titles and IDs.
2. **Connections:** labeled lines describing a handoff or evidence relationship.
3. **Sources:** small citations identifying code, a ticket, logs, or a deployment record.
4. **The Gate:** an explicitly labeled checkpoint showing the approver, decision state, and the boundary between recommendation and action.
5. **Boundaries:** labeled regions showing a team, environment, permission, or execution scope.

Use oxide for the current path, neutral structure for surrounding context, and labelled status treatments for outcomes. Dashed lines represent a proposed action; solid lines represent a recorded relationship. The Gate appears before remediation or another consequential action. Include a legend where both relationship types appear. Do not make a dense network of unexplained nodes the default representation of context.

Follow this grammar in the homepage story, module diagrams, resource illustrations, slides, and event graphics. A static, simplified drawing must remain understandable when motion is disabled or the asset is printed.

## 9. Product imagery, illustrations, and photography

The hero and product sections should show a tangible input, meaningful action, and useful output. Use straight-on, legible screenshot crops with a small number of annotations. Keep realistic field names, sources, and readable text.

Prioritize: actual product capture → carefully redrawn explanatory diagram → editorial illustration. Label conceptual interface studies as illustrative; do not present them as shipped product screenshots. Never invent customer logos, execution records, benchmark results, or support evidence to make a composition look convincing.

Use diagrams for explaining the mechanism and screenshots for proving the experience. Technical animation should explain relationships rather than merely create movement. Reserve photography for the people behind TBSP, real engineering work, and approved customer stories. Use consistent natural light, restrained colour, and composed framing.

Avoid decorative AI brains, generic glowing orbs, unexplained neural networks, robot mascots, illegible tilted screenshots, and stock boardroom images as the principal product explanation. These devices do not demonstrate TBSP's particular value.

## 10. Module identity and icons

Use one master identity with four consistent module lockups:

- TBSP Spec — Explore & define.
- TBSP Code — Build & debug.
- TBSP Review — Review & approve.
- TBSP On-call — Investigate production.

Use a separate surface grammar: TBSP Desktop, TBSP Terminal, TBSP in Slack, TBSP in Teams, and TBSP Mobile where confirmed. Surfaces do not receive peer module logos.

Differentiate modules through names, one consistent line-icon family, and the artifact shown. Suggested conceptual symbols: document for Spec; code brackets for Code; review/check for Review; activity for On-call. Use conversation, terminal, monitor, and phone symbols only for surfaces. Icons supplement the names and never substitute for them. Use a common 24 px construction grid and approximately 1.5–2 px stroke in the eventual icon assets.

Maintain the same typography, colour rules, grid, screenshot framing, and CTA style on every module page. A visitor arriving on On-call should immediately recognize it as the same platform as Code. Use mono eyebrows such as `MODULE / REVIEW` and `SURFACE / SLACK` to make the taxonomy explicit without changing the core design.

## 11. Wordmark and brand architecture

Use TBSP as the working master name until the final naming decision is made. The provisional style specimen uses text, not a final logo.

Recommended logo brief: a confident, compact wordmark and an optional simple symbol based on a frame/path relationship. It should work in one colour, at small size, and without animation. Avoid making a generic terminal prompt the entire identity, since the platform extends beyond coding.

Use an endorsed relationship such as “From Capillary Technologies” in the About/footer context, subject to the final brand decision. Keep module and surface names subordinate to the master brand. Do not create separate module logos or independent visual brands.

For the final logo, establish measured clear space, minimum sizes, monochrome/reverse variants, co-branding lockups, favicon, and misuse examples based on the actual artwork. These cannot be finalized accurately before a mark is selected. Mandatory Capillary identity constraints, if any, are an unresolved input.

## 12. Motion and interaction

- Controls: 120–180 ms transitions, with no large layout movement.
- Small workflow changes: 200–300 ms, anchored to the object that changed.
- Explanatory sequences: user-controlled playback; pause visibly at human approval; show sources or outputs as they appear.
- Reveal a path in the order the workflow is being explained. Do not imply an unattended production action when the product requires a human decision.
- Keep content available immediately. Avoid scroll hijacking, cursor trails, mandatory intro animations, and constantly looping background effects.
- Honour reduced-motion preferences and provide a static equivalent plus captions/transcripts for narrated demonstrations.

Across channels, density and crop change. The type, colour roles, terminology, shapes, and diagram grammar remain stable.

## 14. Consistency rules and handoff package

Keep this guide as the proposed authority for design work until reviewed. The existing product/claims documents remain authoritative for product truth. Record any approved visual decisions with a date; do not silently treat this recommendation as approval.

The brand handoff should include:

1. Approved master name, logo assets, module lockups, and Capillary endorsement rules.
2. Colour, typography, spacing, shape, and motion tokens with examples of allowed pairings.
3. Core web components and their interaction/accessibility states.
4. One diagram kit using artifacts, sources, connections, Gates, and boundaries.
5. Screenshot-capture and annotation rules.
6. Voice examples, terminology, CTA wording, and claim standards.
7. Home, module, technical-information, resource, and documentation templates.
8. Matching presentation, social, one-pager, and event templates.

Review the identity on a homepage hero, a module page, a dense technical page, and a small social/event crop before declaring it complete. It must remain recognizable without a logo and remain readable when printed, reduced, or viewed on a phone.

## 15. Assumptions and remaining choices

- The full known product capability set is in V1, organised as Spec, Code, Review, and On-call plus Surfaces.
- Debugging remains an anchored section and flagship walkthrough within Code.
- Slack is a surface rather than a peer module; the same treatment applies to desktop, terminal, Teams, and mobile as confirmed.
- The shared foundation requires a product-grade name. Story PR remains a working review-artifact name pending validation.
- The product has a distinct identity with a visible Capillary relationship; mandatory parent-brand visual constraints have not been supplied.
- India and US buyers share one initial English-language identity; this is not a claim that either market has a universal aesthetic preference.
- The target includes engineering leadership, technical champions, developers, and security reviewers. The visual system must serve that whole evaluation path.
- Product access and pricing are separate decisions. The style specimen uses product-exploration language and does not establish a free offer.
- This document defines the recommended language and rules. Final naming, logo drawing, exact brand endorsement, and a production component library remain subsequent design work.
- The reference sites demonstrate design approaches, not proof of what will work commercially for TBSP. Validate comprehension with representative buyers and technical evaluators.
